# 의상 속성 기반 추천 규칙

> 현재 코드에 구현된 규칙을 정리한 문서다. 온도 구간과 점수는 초기 정책이며 추후 조정할 수 있다.

## 1. 목적 및 적용 범위

날씨와 온도 민감도로 보정 온도를 계산하고, 의상의 두께 수준에 따라 적합한 의상 조합을 선택한다. 선호 두께가 없으면 정해진 차선 순서로 선택하며, 부적합한 두께도 마지막 후보로 유지한다. LLM은 사용하지 않는다.

속성은 관리자가 자유롭게 등록할 수 있으며, 추천을 위해 특정 속성을 미리 생성할 필요는 없다. 단, 규칙 사전에 등록된 속성명과 선택값만 두께 정보로 해석한다.

추천 서비스는 날씨와 프로필, 사용자 소유 의상을 조회하고, 각 의상의 속성을 분석·종합하여 속성 기반 추천 메서드에 전달한다. 분석 결과는 별도로 저장하지 않고 요청마다 계산한다.

### 서비스 처리 흐름

```text
날씨·프로필·사용자 소유 의상 조회
→ 소유 의상 ID 목록으로 속성과 정의 일괄 조회
→ 속성별 두께 해석 및 의상 ID별 그룹화
→ 의상별 두께 종합
→ 속성 기반 알고리즘 호출
→ 선택된 의상을 응답 DTO로 변환
```

보유 의상이 없으면 속성 조회를 생략한다. 속성이 없는 의상은 빈 두께 목록을 종합하여 `UNKNOWN`으로 전달한다. 의상 속성값이나 정의 이름이 바뀌면 다음 요청에서 조회한 최신 값으로 다시 분석한다. 분석 결과 저장, 규칙 버전 관리, 일괄 재분석은 이번 정책의 범위에 포함하지 않는다.

## 2. 속성 해석

`AttributeSemanticAnalyzer`는 속성명과 선택값을 함께 확인하여 `ThicknessLevel`을 반환한다.

| 속성명 | 선택값 | 반환값 |
| --- | --- | --- |
| 두께, 두께감 | 얇음 | LIGHT |
| 두께, 두께감 | 보통 | MEDIUM |
| 두께, 두께감 | 두꺼움, 도톰함 | HEAVY |
| 그 외 속성명 또는 선택값 | 모든 값 | UNKNOWN |

적용 규칙은 다음과 같다.

- 속성명과 선택값의 앞뒤 공백을 `strip()`으로 제거한다. 중간 공백은 제거하지 않는다.
- 사전과 정확히 일치하는 표현만 사용한다. 부분 문자열로 의미를 추측하지 않는다.
- 속성명이나 선택값이 `null`이면 `UNKNOWN`을 반환한다. 빈 문자열도 사전에 없으므로 `UNKNOWN`이다.
- 동의어를 추가하려면 규칙 사전을 수정한다. 새로운 표현마다 enum을 추가하지 않는다.

예를 들어 `두께감=도톰함`은 `HEAVY`지만, `가격대=두꺼움`이나 `두께=두꺼움 아님`은 `UNKNOWN`이다.

## 3. 의상별 두께 정보 종합

`ClothesThermalEstimator`는 한 의상에서 해석한 두께 수준 목록을 입력받는다. 문자열 해석이나 DB 조회는 수행하지 않는다.

| 입력 예시 | 반환값 | 적용 규칙 |
| --- | --- | --- |
| LIGHT | LIGHT | 유효한 수준 사용 |
| HEAVY, HEAVY | HEAVY | 동일 수준은 중복 반영하지 않음 |
| UNKNOWN, LIGHT | LIGHT | UNKNOWN은 종합 과정에서 제외 |
| LIGHT, HEAVY | UNKNOWN | 서로 다른 유효 수준이 있으면 충돌 처리 |
| HEAVY, HEAVY, LIGHT | UNKNOWN | 개수가 많아도 충돌을 무시하지 않음 |
| UNKNOWN만 있거나 빈 목록 | UNKNOWN | 판단할 정보 없음 |

`UNKNOWN`은 두께를 모른다는 뜻이며 `MEDIUM`과 구분한다. 보온성 판단에는 두께 수준을 사용하며, 실제 단열 성능을 측정하거나 소재·계절을 평가하지 않는다.

## 4. 보정 온도 계산

`BasicOutfitAlgorithm`은 다음 식으로 온도 민감도를 반영한다.

```text
보정 온도 = 실제 기온 + (온도 민감도 - 3) × 2.0
```

| 실제 기온 | 민감도 | 보정 온도 |
| --- | --- | --- |
| 17℃ | 1 | 13℃ |
| 17℃ | 3 | 17℃ |
| 17℃ | 5 | 21℃ |

이 식에서는 민감도 값이 클수록 보정 온도가 높아진다. 추천 서비스는 민감도가 없으면 기본값 `3`을 사용한다.

속성 기반 추천에서는 보정 온도를 한 번 계산하여 두께 적합도와 아우터 추가 여부에 공통으로 사용한다. 적합도 계산기는 전달받은 보정 온도를 다시 보정하지 않는다. 민감도는 중간 온도 구간의 차선 순위를 정할 때만 추가로 사용한다.

## 5. 두께 적합도 및 차선 선택

선호 두께가 없으면 보통 두께, 개인별 차선, UNKNOWN, 남은 두께를 온도 구간별 우선순위에 따라 선택한다.

### 5.1 온도와 민감도의 적용 순서

1. 기존 식으로 보정 온도를 한 번 계산한다.
2. 보정 온도로 추움·중간·더움 구간을 결정한다.
3. 추운 구간과 더운 구간에서는 선호 두께 다음으로 보통 두께를 선택한다.
4. 중간 구간에서는 보통 두께를 우선하고, 보통 두께가 없으면 민감도로 차선을 정한다.
5. 민감도가 중립이면 보정 온도 20℃를 기준으로 차선을 정한다.

민감도는 보정 온도 계산 외에 **중간 구간의 차선 순위 결정에만** 추가로 사용한다. 민감도로 온도를 다시 보정하거나 추움·더움 구간의 선호 두께를 뒤집지 않는다.

| 민감도 | 현재 코드 방향에 따른 분류 | 중간 구간에서 보통 두께 다음으로 선택 |
| --- | --- | --- |
| 1·2 | 추위를 타는 방향 | HEAVY |
| 3 | 중립 | 보정 온도 20℃ 미만은 HEAVY, 20℃ 이상은 LIGHT |
| 4·5 | 더위를 타는 방향 | LIGHT |
| 미설정 | 기본값 3 적용 | 중립과 동일 |

20℃는 중간 구간인 15~25℃를 나눈 초기 정책 기준이며, 실제 체감 온도를 보장하는 값은 아니다.

### 5.2 최종 두께 우선순위

각 의상 종류에서 아래 순서대로 보유 후보를 선택한다. 앞 순위의 후보가 없으면 다음 순위로 진행한다.

| 보정 온도 | 민감도 조건 | 우선순위 |
| --- | --- | --- |
| 15℃ 미만 | 모든 민감도 | HEAVY → MEDIUM → UNKNOWN → LIGHT |
| 15℃ 이상, 25℃ 미만 | 1·2 | MEDIUM → HEAVY → UNKNOWN → LIGHT |
| 15℃ 이상, 20℃ 미만 | 3 | MEDIUM → HEAVY → UNKNOWN → LIGHT |
| 20℃ 이상, 25℃ 미만 | 3 | MEDIUM → LIGHT → UNKNOWN → HEAVY |
| 15℃ 이상, 25℃ 미만 | 4·5 | MEDIUM → LIGHT → UNKNOWN → HEAVY |
| 25℃ 이상 | 모든 민감도 | LIGHT → MEDIUM → UNKNOWN → HEAVY |

- 중간 구간에서 보통 두께가 없으면 민감도 또는 20℃ 기준으로 정한 두께가 차선이다.
- 선호·차선 후보가 모두 없으면 UNKNOWN을 남은 반대 두께보다 우선한다. UNKNOWN이 적합하다고 보장하는 것은 아니다.
- 부적합한 두께도 후보에서 제거하지 않는다. 다른 후보가 없으면 마지막 대안으로 반환한다.
- 같은 순위의 후보끼리는 기존처럼 입력 순서를 유지한다.
- 상의·하의 우선, 원피스 대체, 아우터 추가 온도 등 코디 구성 규칙은 유지한다.
- 빈 결과는 기존처럼 기본 조합 자체를 구성할 수 없는 경우에 반환한다.

적합도는 위 우선순위에 따라 다음 점수를 부여한다. 후보가 없더라도 남은 후보의 점수를 다시 계산하지 않는다.

| 순위 | 의미 | 점수 |
| --- | --- | --- |
| 1순위 | 보정 온도의 선호 두께 | 3 |
| 2순위 | 보통 두께 또는 중간 구간의 개인별 차선 | 2 |
| 3순위 | UNKNOWN | 1 |
| 4순위 | 남은 반대 두께 | 0 |

예를 들어 더운 날에 LIGHT가 없어도 MEDIUM은 2점, UNKNOWN은 1점, HEAVY는 0점을 유지한다. 0점인 의상만 있어도 기본 조합을 구성할 수 있으면 반환한다. 테스트는 온도·민감도별 순위와 최종 선택 결과를 검증한다.

### 5.3 적용 예시

| 상황 | 후보 | 선택 결과 |
| --- | --- | --- |
| 보정 온도 28℃ | HEAVY, MEDIUM | MEDIUM |
| 보정 온도 10℃ | LIGHT, MEDIUM | MEDIUM |
| 실제 21℃·민감도 1 → 보정 17℃ | LIGHT, HEAVY | HEAVY |
| 실제 19℃·민감도 5 → 보정 23℃ | HEAVY, LIGHT | LIGHT |
| 보정 온도 19℃·민감도 3 | LIGHT, HEAVY | HEAVY |
| 보정 온도 20℃·민감도 3 | HEAVY, LIGHT | LIGHT |
| 보정 온도 28℃ | HEAVY, UNKNOWN | UNKNOWN |
| 보정 온도 28℃ | HEAVY만 있음 | HEAVY |

예시는 같은 종류 안에서의 후보 선택을 의미한다. 상의가 선택되어도 하의나 원피스가 없어 기본 조합을 구성할 수 없다면 최종 결과는 빈 목록이다.

## 6. 의상 조합 선택

속성 기반 추천 메서드는 의상 목록, 의상 ID별 두께 수준, 실제 기온, 온도 민감도를 입력받는다.

```text
보정 온도 계산
→ 두께 적합도 내림차순으로 의상 목록 정렬
→ 종류별 첫 번째 후보 선택
→ 기본 조합 구성
→ 필요한 경우 아우터 추가
```

### 6.1 후보 및 동점 처리

- 의상 ID에 대응하는 두께 정보가 없거나 의상 ID가 없으면 `UNKNOWN`으로 평가한다.
- 점수가 같으면 입력 목록의 순서를 유지한다. 의상 ID로 동점을 정렬하지 않는다.
- 두께를 모르는 의상도 후보에서 제외하지 않는다.
- 후보의 적합도가 낮아도 조합을 구성할 수 있으면 추천한다. 최소 적합도 제한은 없다.
- 다른 종류의 의상도 하나의 목록에서 정렬하지만, 최종 선택은 각 종류의 첫 번째 후보를 사용한다.

예를 들어 더운 날에 두 반팔이 모두 LIGHT로 같은 순위이면, 입력 목록에서 먼저 나온 반팔을 선택한다. DB 조회 순서에 따라 입력 순서가 달라질 경우 동점 선택 결과도 달라질 수 있다.

### 6.2 기본 조합 및 아우터

| 조건 | 반환 조합 |
| --- | --- |
| 상의와 하의가 모두 있음 | 상의 1개 + 하의 1개 |
| 상의·하의 조합이 불가능하고 원피스가 있음 | 원피스 1개 |
| 기본 조합을 구성할 수 없음 | 빈 목록 |
| 기본 조합이 있고 보정 온도가 15℃ 미만이며 아우터가 있음 | 기본 조합 + 아우터 1개 |

상의·하의와 원피스가 모두 있어도 상의·하의 조합을 우선한다. 기본 조합 없이 아우터만 반환하지 않으며, 아우터가 없으면 기본 조합만 반환한다. 보정 온도가 정확히 15℃이면 아우터를 추가하지 않는다.

신발·가방·액세서리 등은 현재 조합에 포함하지 않는다.

### 6.3 기존 추천 메서드

- 두께 정보 없이 기온·민감도만 받는 메서드는 입력 순서대로 기본 조합을 선택하고 아우터 추가 여부를 판단한다.
- 의상 목록만 받는 메서드는 입력 순서대로 기본 조합만 선택한다. 날씨 판단과 아우터 추가는 수행하지 않는다.
- 알고리즘 자체는 소유권을 검사하지 않는다. 추천 서비스가 사용자 ID로 조회한 소유 의상을 후보로 전달한다.

## 7. 검증 기준

- 선호 두께가 없으면 보통 두께를 선택한다.
- 중간 구간에서 보통 두께가 없으면 민감도에 따라 차선을 선택한다.
- 중립 민감도는 보정 온도 20℃ 미만과 이상에서 차선이 달라진다.
- 15℃·20℃·25℃ 경계가 정책의 구간에 정확히 포함된다.
- 선호·차선 후보가 없으면 UNKNOWN을 반대 두께보다 우선한다.
- 반대 두께만 있어도 기본 조합을 만들 수 있으면 추천한다.
- 같은 순위의 후보는 입력 순서를 유지한다.
- 민감도는 온도 보정에 한 번만 적용하고, 중간 구간의 차선 결정에 별도로 사용한다.
- 기본 조합·아우터 규칙과 사용자 소유 의상 제한을 유지한다.

### 검증 범위 및 실행 방법

| 구분 | 검증 범위 |
| --- | --- |
| 계산기·알고리즘 단위 테스트 | 온도·민감도별 전체 순위, 15·20·25℃ 경계, 종류별 차선·동점 선택 |
| 서비스 테스트 | 속성 일괄 조회, 의상별 두께 전달, 실제 알고리즘 연결, 민감도 기본값 |
| DB·API 통합 테스트 | 저장된 속성 기반 차선 선택, 다른 사용자 의상 제외, 민감도와 20℃ 경계, 속성 수정 후 재추천, UNKNOWN 우선, 후보 부족 처리 |

통합 테스트는 테스트 전용 PostgreSQL과 실제 서비스·알고리즘·JWT 필터를 사용한다. Redis의 토큰 등록 여부만 대체하므로 실제 로그인·Redis 세션 전체를 검증하는 테스트는 아니다. 데이터 저장·수정 후 `flush()`와 `clear()`를 호출하여 DB에서 다시 읽는 흐름을 검증하며, 테스트 트랜잭션은 종료 시 롤백된다.

```bash
# 추천 관련 단위·서비스·컨트롤러·DB/API 통합 테스트
./gradlew test --tests 'com.otboo.team03.recommendation.*'

# 추천 DB/API 통합 테스트만 실행
./gradlew test --tests '*RecommendationIntegrationTest'

# 전체 회귀 테스트
./gradlew test
```

DB·API 통합 테스트를 실행하려면 Docker가 실행 중이어야 한다. 전체 테스트에는 다른 도메인의 DB·Redis 등 추가 실행 환경이 필요할 수 있다.

## 8. 별도 검토 범위

- 요청별 분석에 성능 문제가 확인되면 분석 결과 저장과 재분석 정책을 검토한다.
- 소재·소매 길이·계절은 지원 규칙과 중복 반영 기준을 정한 후 별도 확장한다.
