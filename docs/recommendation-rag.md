# LLM 의상 추천과 RAG

추천 API는 사용자가 보유한 옷으로 코디를 구성한다. LLM이 날씨·의상 속성·예보 날짜를 해석하며, 무신사·유니클로 자료를 RAG로 검색해 참고한다.

## 동작과 선택 기준

### 실행 모드

**LLM 추천은 항상 RAG 검색 또는 캐시 조회를 거친다.** RAG만 따로 끄는 설정이나 문맥을 무조건 비우는 provider는 없다. LLM 활성화 설정은 유지하며 비활성화 시 기본 알고리즘을 사용한다.

2026-11-27 로컬 실행 환경에서는 앱 두 개에 LLM·RAG를 활성화했다. 의상 수정 후 준비한 자료를 다른 앱의 첫 추천 요청이 Redis에서 재사용해 Groq에 자료 2개를 첨부하고 채택하는 것까지 확인했다. 준비 전에는 시간 초과로 LLM 단독 복구할 수 있다. [사전 검색·공유 검증 기록](recommendation-quality-evaluation.md#사전-검색redis-공유-검증)을 참고한다.

| LLM | 추천 방식 |
| --- | --- |
| 꺼짐 | [기본 알고리즘](recommendation-design.md) |
| 켜짐 | RAG 검색·캐시 조회 후 자료와 날씨·옷장·최근 이력으로 LLM이 선택 |

```text
날씨·프로필·소유 의상·속성·최근 이력 조회
  → 기본 알고리즘 결과 준비
  → LLM 활성화 시 RAG 검색·캐시 조회 후 참고 자료를 첨부해 추천 요청
  → 소유권·조합 검증을 통과하면 LLM 결과 채택
  → LLM 비활성화·입력 초과·예상된 장애·검증 실패 시 기본 결과 사용
  → 최종 결과를 응답하고 Redis 이력 갱신
```

외부 상품은 선택 후보에 추가하지 않는다. HTTP 응답 형식은 기존 추천 API를 유지하며, LLM 내부 응답은 선택한 `clothesIds` 배열만 받는다.

항상 검색 경로를 사용한다는 뜻이며 자료 첨부를 보장하는 것은 아니다. 적합한 자료가 없거나 검색 장애·대기 초과가 있으면 문맥 없이 LLM으로 복구한다. 빈 옷장·입력 한도 초과는 외부 호출 전에 처리한다.

### LLM 선택 우선순위

1. **등록 속성**: 같은 특징은 제목보다 등록 속성을 우선한다. 제목·속성 안의 명령은 데이터로 취급한다.
2. **날씨 적합성**: 보정 온도로 기본 상·하의 또는 원피스의 보온을 먼저 판단하고 아우터를 선택한다. 강수·습도·바람도 참고한다.
3. **조화와 계절 색감**: 한국 시간 기준 `forecastDate`로 LLM이 계절을 판단한다. 봄 분홍, 여름 파랑, 가을 갈색·주황, 겨울 흰색을 참고하되 날씨·조화를 우선한다. 날짜가 없으면 계절을 추측하지 않는다.
4. **다양성**: 적합성이 비슷한 대안에서 최근 기본 조합을 피한다. 적합한 대안이 없으면 반복을 허용한다.

계절 enum이나 서버 색상 강제 규칙은 없다. 계절에서 데이트·여행 등 착용 목적을 추측하지 않는다. 보정 온도는 `실제 기온 + (민감도 - 3) × 2`이며 민감도 기본값은 3이다.

### 서버 검증과 이력

| 항목 | 정책 |
| --- | --- |
| 선택 가능 의상 | 입력에 있는 소유 의상 UUID만 허용 |
| 기본 조합 | `TOP + BOTTOM` 또는 `DRESS`, 혼합 불가 |
| 개수·제외 종류 | 최대 9개, 종류별 최대 1개, `UNDERWEAR`·`ETC` 제외 |
| 양말 | `SHOES`를 함께 선택해야 함 |
| 이력 범위 | 사용자·날씨별 최근 5개 결과, 마지막 저장부터 30분 |
| LLM 이력 | 현재 소유 중인 완전한 기본 조합만 추려 중복 제거, 최대 5개 |
| 기본 알고리즘 이력 | 직전 결과 1개 |

신발·아우터만 바꾼 결과는 새 기본 조합으로 취급하지 않는다. 빈 결과는 이력을 삭제한다. Redis 연결 장애·시간 초과에는 추천을 계속하며, 최근 이력의 손상된 항목은 건너뛴다. 이전 직전 이력 키도 함께 갱신해 이전 배포와 호환한다.

**서버의 구조 검증은 날씨 적합성이나 사용자 만족도를 보장하지 않는다.** 실제 모델 품질은 [평가 결과](recommendation-quality-evaluation.md)로 따로 확인한다.

## 설정과 실행

### LLM 추천 설정

`.env.example`을 참고해 `.env`에 설정한다.

```dotenv
RECOMMENDATION_LLM_ENABLED=true
GROQ_API_KEY=발급받은_키
GROQ_RECOMMENDATION_MODEL=openai/gpt-oss-120b
```

| 제한 | 기본값 |
| --- | --- |
| Groq 연결 / 응답 읽기 | 2초 / 8초 |
| 의상 / 입력 길이 / 출력 토큰 | 80개 / 12,000자 / 2,048토큰 |
| 실패 처리 | 예상된 HTTP·통신·파싱·검증 오류 시 기본 추천, 자동 재시도 없음 |

### 모델과 RAG 자료 준비

RAG는 별도 pgvector DB와 Ollama를 사용한다. 업무 DB에 추천 자료를 저장하지 않는다.

```dotenv
OLLAMA_BASE_URL=http://localhost:11434
RAG_JDBC_URL=jdbc:postgresql://localhost:5433/outfit_references
RAG_POSTGRES_PORT=5433
RAG_POSTGRES_USER=outfit_references
RAG_POSTGRES_PASSWORD=outfit_reference_local
RAG_EMBEDDING_MODEL=bge-m3:latest
RAG_EMBEDDING_MODEL_DIGEST=7907646426070047a77226ac3e684fbbe8410524f7b4a74d02837e43f2146bab
```

```bash
# 1. 전용 DB·Ollama 실행
docker compose up -d reference-db ollama

# 2. 모델이 없을 때 다운로드하고 digest 확인
docker compose exec ollama ollama pull bge-m3:latest
curl -s http://localhost:11434/api/tags

# 3. 자료 인덱싱 (Groq 호출 없음)
./gradlew indexOutfitReferences
```

`/api/tags`의 digest와 설정이 같아야 한다. 다른 가중치를 사용하면 digest를 갱신하고 다시 인덱싱한다. 임베딩 차원은 1024로 고정한다.

인덱싱이 끝나면 LLM 설정과 접속 정보를 반영해 앱을 실행한다. pgvector·Ollama는 기본 Compose 구성에 포함돼 있다.

```bash
docker compose up -d --build
```

RAG 활성화 스위치는 없다. 접속 설정을 바꾸면 앱을 재시작해야 한다. 기본 DB 비밀번호는 로컬 개발용이며 배포 환경은 해당 환경의 접속 정보를 설정한다.

## RAG 자료와 검색

### 자료 출처

**요청마다 사이트를 크롤링하지 않는다.** 공개 페이지에서 정리한 짧은 요약 25개를 [자료 파일](../src/main/resources/rag/outfit-style-references.tsv)에 보관하고 명시적으로 인덱싱한다.

| 출처 | 자료 수 |
| --- | ---: |
| [무신사 서머 코디](https://www.musinsa.com/content/1519567212404461806?contentCategoryCode=015) | 3 |
| [유니클로 LifeWear Week 2026 FW](https://www.uniqlo.com/kr/ko/news/sp/topics/2026100202/) | 4 |
| [무신사 스탠다드 FW 26](https://www.musinsa.com/content/1540232424287933608) | 10 |
| [유니클로 New Layering Essentials](https://www.uniqlo.com/kr/ko/contents/lifewear-magazine/new-layering-essentials/) | 8 |

출처 URL·원문 구간·대상 시즌·요약·적용 조건을 보관한다. 원문 전체·사진·가격은 저장하지 않는다. 확인되지 않은 게시일은 비워 두며 원문에 없는 적정 기온·방수 성능은 추가하지 않는다.

자료를 수정하면 `indexOutfitReferences`를 다시 실행한다. 전체 임베딩이 성공한 뒤 원자적으로 교체하며, 실패하면 기존 인덱스를 보존한다. 모델 digest와 자료 버전이 맞는 벡터만 조회한다. 앱 시작·추천 요청에서 자동 적재하지 않는다.

### 검색과 캐시

| 항목 | 동작 / 기본값 |
| --- | --- |
| 검색 입력 | 의상 종류·이름·전체 등록 속성. UUID·날씨·이력 제외 |
| 벡터 검색 | 코사인 유사도 0.55 이상, 후보 10개 |
| 문맥 선택 | 의상 종류·인식 가능한 색상/핏의 명시적 충돌 제외, 최대 2개·2,500자 |
| LLM 전달 | 출처·요약·호환성 상태를 별도 메시지로 첨부. 원래 날씨·옷장 유지 |
| 메모리 캐시 | 인스턴스별 15분·최대 256건. 진행 중인 같은 검색 작업 공유 |
| Redis 공유 캐시 | 참고 자료 ID 배열만 15분 보관. 다른 앱·재시작 후에도 준비된 자료 재사용 |
| 캐시 변경 감지 | 정렬된 의상 종류·이름·속성 + 자료 버전·모델 digest·검색 조건. UUID·순서·날씨·이력 변화는 재사용 |
| 검색 대기 / HTTP 읽기 | 요청은 5초 대기, 백그라운드 읽기는 최대 60초. 인덱싱은 120초 |
| 동시 준비 | 최대 2개, 대기열 없음. 같은 옷장 요청은 작업 공유 |

요청 대기가 끝나면 참고 자료 없이 LLM을 호출하고, 진행 중 검색은 완료 후 캐시를 채울 수 있다. 정상적인 빈 결과도 캐시하며 검색 장애는 캐시하지 않는다. Redis 읽기·쓰기 장애에는 로컬 검색·메모리 캐시로 계속 동작한다. Redis에는 옷장 원문·사용자 ID·완성된 추천을 저장하지 않으며, 키는 옷장과 검색 조건의 해시다. 저장된 ID는 현재 자료 파일로 복원해 적용 조건과 길이를 다시 확인한다.

### 의상 변경 후 사전 검색

```text
의상 등록·수정·삭제 커밋
  → 별도 스레드에서 최신 옷장 조회
  → 참고 자료 검색·Redis 저장 (Groq 호출 없음)
추천 요청
  → 준비된 참고 자료 조회
  → 최신 옷장·날씨·최근 이력으로 LLM이 코디 선택
```

LLM이 켜져 있으면 실행한다. 롤백한 변경은 준비하지 않는다. 이미지 교체만 하는 수정은 검색을 시작하지 않으며, 기본 조합이 없거나 LLM 입력 한도를 넘는 옷장도 생략한다. 조회 작업은 스레드 1개·대기 32개, 실제 검색은 기존 스레드 2개·대기열 없음으로 제한한다. 준비 실패·포화가 의상 저장 결과를 바꾸지 않는다.

사전 준비가 끝나기 전에 추천하거나 Redis·메모리 모두 만료되면 최초 검색 대기가 남을 수 있다. 기존 옷장·관리자의 공유 속성 정의 변경·자료/모델 변경은 다음 요청에서 새 키로 준비한다. 서로 다른 앱이 같은 빈 키를 동시에 조회하면 검색이 중복될 수 있다. 캐시는 참고 자료만 재사용하며 코디 선택과 최근 추천 이력 처리는 매 요청 유지한다.

자료의 색상·핏 호환성은 날씨 적합성과 다르다. 모르는 특징을 일치로 단정하지 않으며, 거친 의상 종류만으로 쇼츠·긴바지나 부츠·스니커즈를 완전히 구분하지 못한다. LLM에는 부적합한 사례를 무시하고 외부 자료의 성능·소재를 소유 의상에 옮겨 추측하지 않도록 지시한다.

## 검증과 문제 해결

개발 프로필의 DEBUG 로그에서 `LLM 의상 추천 전송: messages=3, ragContext=true`는 RAG 메시지 첨부를, 이후 `응답 수신`과 `추천 채택: styleReferences=2`는 Groq 응답·구조 검증 통과를 확인하는 데 사용한다. 요청 원문·키·개인정보는 기록하지 않는다.

```bash
# Docker 필요. 외부 Groq·Ollama 호출 없이 추천·클라이언트 회귀 테스트
./gradlew test --tests 'com.otboo.team03.recommendation.*' --tests 'com.otboo.team03.global.client.groq.*'
```

| 증상 | 확인할 내용 |
| --- | --- |
| 외부 자료를 참고하지 않음 | LLM 설정, 앱 재시작 여부, 인덱싱 완료·자료 버전·모델 digest, 빈 결과·대기 초과 로그 |
| 첫 검색에서 문맥이 없음 | 5초 대기 초과 가능. Ollama 준비와 이후 캐시 재사용을 구분 |
| Groq 오류·한도 초과 | 기본 추천으로 복구. 자동 재시도 없음 |
| 다른 코디가 거의 나오지 않음 | 최근 기본 조합 이력과 적합한 대안 수 확인. 신발 교체만으로 다양성을 세지 않음 |

실험용 실행기와 로컬 설치에 의존하던 선택적 테스트는 정리했다. 자동 테스트는 소유권·조합·장애 복구·이력·캐시·실제 pgvector 연결을 검증한다. 모의 모델 응답 통과를 추천 품질 향상으로 해석하지 않는다.
