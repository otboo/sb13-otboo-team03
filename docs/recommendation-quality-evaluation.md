# 의상 추천 성능 검증 정리

> **최신 재검증(2026년 11월 25일): 기존 추천 15/24, LLM 연동 추천 24/24.**
> 비 대응과 의상별 근거 인용 지시를 보강한 뒤 전체 조건을 통과했다. 추가 비 반복 4/4·아우터 없는 비 대조 2/2도 통과했다.

## 비교 결과

같은 옷장·날씨·사용자 조건으로 기존 추천과 LLM 연동 추천을 비교했다. **12개 상황 × 입력 순서 2가지 = 24회**이며, 상황별 조건을 모두 지키면 통과로 계산했다. 최신 평가는 프롬프트와 통과 기준을 고정하고 실행했다. 기존 알고리즘은 각 회차까지 이전 기록과 동일하게 재현됐다.

| 확인한 항목 | 기존 알고리즘 | 비 대응 보강 전 | 비 대응 보강 후 |
| --- | --- | --- | --- |
| 최종 추천이 상황 조건을 지킴 | 15/24 · 62.5% | 23/24 · 95.8% | **24/24 · 100%** |
| LLM 응답이 서버 검사를 통과해 사용됨 | 해당 없음 | 23/24 | 24/24 |
| 근거 문구 오류로 응답을 사용하지 못함 | 해당 없음 | 1건 | 0건 |
| Groq HTTP 오류 | 해당 없음 | 0건 | 0건 |
| LLM 처리 시간 중앙값 | 측정 대상 아님 | 약 1.93초 | 약 1.97초 |

최종 추천은 호출·검증 실패 시 기존 알고리즘으로 복구한 결과도 포함한다. **이번 24회는 모두 HTTP 200·서버 채택이었고 기본 추천으로 복구한 회차는 없었다.** 이전에 실패한 C07은 두 순서 모두 방수 재킷과 레인 부츠를 선택했다. 별도 추가 반복 4회도 같은 조건을 통과해 C07은 총 6/6이며, 추가 4회와 아우터 없는 대조 2회는 위 24회에 합산하지 않았다.

## 무엇을 확인했나

| 확인 대상 | 통과 예시 |
| --- | --- |
| 기온·민감도 | 더운 날 겨울옷을 피하고, 추위를 타는 사용자의 보온을 고려 |
| 제목·자유 속성 | 비에는 방수 의상, 강풍에는 방풍 아우터 활용 |
| 충돌하는 정보 | 제목보다 사용자가 등록한 속성을 우선 |
| 조합의 기본 조건 | 소유한 옷으로 조합하고 속옷·기타 물품을 제외 |

HTTP 정상 응답, 서버 검사 통과, 추천 품질은 각각 확인한다. 예를 들어 강풍에 상의·하의만 고른 응답은 조합·근거 검사를 통과해도 방풍 재킷 선택 조건에서는 실패할 수 있다.

## 발견한 문제와 현재 상태

| 문제 | 반영한 개선 | 확인된 결과·남은 점 |
| --- | --- | --- |
| 다른 의상의 속성을 근거로 인용 | 분석 ID에 해당하는 의상만 먼저 찾도록 프롬프트·스키마 설명 보강 | 이전 C07 오류 1건, 최신 전체 24회·추가 6회는 근거 오류 0건 |
| 비 오는 날 방수 아우터 누락 | 비 대비를 보온과 구분하고 아우터·신발을 각각 검토 | C07 두 순서와 추가 4회 모두 재킷·레인 부츠 선택 |
| 제목과 등록 속성이 충돌할 때 잘못 판단 | 같은 특징은 등록 속성을 우선 | 최신 C11 두 입력 순서 모두 통과 |
| 강풍에서 아우터 누락 | 날씨 우선 판단과 실제 선택 목록 재확인 지시 | 최신 C08 두 입력 순서 모두 방풍 재킷 선택 |
| HTTP 400 발생 | 안전한 오류 로그 추가, UUID 방식 유지 | **과거 두 건 모두 반환 의상 ID의 enum 위반으로 확인**. 최신 24회에서는 오류 0건 |
| 추위 민감도 반영이 일관되지 않음 | 공통 정책으로 계산한 보정 온도 전달 | C04는 변경 전 두 순서 실패 → 이번 두 순서 모두 보온 상·하의와 재킷 선택 |

UUID·공통 보정 온도 전달과 기존 서버 검증을 유지했다. 이번에는 비 대응 지시와 의상별 근거 설명을 함께 보강했으며, 프롬프트·스키마 설명·통과 조건은 실행 중 바꾸지 않았다. 관련 테스트 130개도 통과했다.

## 결과를 해석할 때

- 이 수치는 **만든 상황에서 조건을 지킨 비율**이다. 실제 사용자 만족도·색 조합·전체 추천 정확도를 뜻하지 않는다.
- 입력 순서만 바꾼 두 결과는 독립적인 사용자 사례가 아니다. C04의 17℃·민감도 1·보정 13℃와 C11의 충돌 조건은 프롬프트 예시에도 포함돼 있다.
- 추가 반복·대조의 성공률은 전체 24회 평가와 합치지 않는다. 프롬프트와 스키마 설명을 함께 변경했으므로 개별 변경의 인과 효과나 전체 사용자 성능 향상으로 단정하지 않는다.

## 다음에 다시 검증하는 방법

1. 아래 상세 자료의 12개 옷장과 두 입력 순서를 준비하고, 통과 조건을 먼저 고정한다.
2. 두 방식에 같은 날씨·민감도·직전 추천 기록을 적용한다. API로 비교하면 `RECOMMENDATION_LLM_ENABLED`를 각각 `false`, `true`로 설정하고 서버를 재시작한다.
3. LLM 원래 선택, 서버 채택 여부, 최종 반환 의상, 복구 원인과 조건 통과 여부를 함께 기록한다. 실패한 요청을 재시도한 성공 결과로 교체하지 않는다.
4. 전체 통과 횟수와 새로 실패한 사례를 비교하고, 프롬프트·모델·평가 조건 중 무엇을 바꿨는지 명시한다.

| --- | --- | --- | --- | --- |
| 예: C08 · 순서 1 | 기록 | 기록 | 기록 | 기록 |

**확인한 비·민감도 실패 사례는 이번 고정 조건 평가에서 모두 통과했다.** 구현 구조·설정·단위 테스트 실행 방법은 [LLM 추천 구현 문서](recommendation-rag.md)를 참고한다.

강풍 비교는 첫 반복에 이전 → 수정, 두 번째 반복에 수정 → 이전 순서로 실행했다. 마지막 실험은 첫 6회에서 설명 오류를 관찰한 뒤 별도 6회로 재확인했다. 각 실험에서 요청 간격은 30초, 요청당 호출은 1회였다.

### 후속 사례의 입력

아래 사례는 민감도 3, 직전 추천 ID는 빈 집합이며 CLEAR·NONE·강수 확률 0%·습도 50%다. 의상 ID 생성 방식은 위와 같다.

**W01 · 12℃·풍속 8m/s:** 등록 속성에 따라 바람을 막는 재킷을 고르고 성긴 가디건을 제외한다. 순서 1은 아래 표의 순서다.

| 키 | 의상 제목 | 종류 | 등록 속성 |
| --- | --- | --- | --- |
| `open_outer` | 방풍 스타일 가디건 | OUTER | 두께=보통, 조직=성긴 짜임으로 바람이 잘 통함 |
| `bottom` | 코튼 팬츠 | BOTTOM | 두께=보통 |
| `wind_outer` | 데일리 재킷 | OUTER | 두께=보통, 원단 성질=바람을 막는 촘촘한 짜임 |
| `top` | 면 긴팔 셔츠 | TOP | 두께=보통, 소매=긴팔 |

W01은 같은 입력을 반복했고 역순을 추가하지 않았다. W01·W02의 구체적인 옷장 데이터는 프롬프트 예시로 넣지 않았다.

**W02 · 31℃·풍속 2m/s:** C09의 의상에 `winter_outer`(방풍 겨울 패딩, OUTER, 두께=두꺼움·기능=방풍)을 추가한다. 겨울 패딩·겨울 부츠·겨울 울 양말을 제외해야 한다. 입력 순서는 `winter_outer` → `summer_socks` → `bottom` → `winter_socks` → `top` → `summer_shoes` → `winter_shoes`이며 같은 순서를 반복했다.

**W03 · 24℃·풍속 null:** 겨울 패딩을 피하고, 풍속을 모른다는 사실을 설명에서도 유지하는지 확인한다. 순서 1은 아래 표, 순서 2는 역순이다.

| 키 | 의상 제목 | 종류 | 등록 속성 |
| --- | --- | --- | --- |
| `winter_outer` | 두꺼운 방풍 겨울 패딩 | OUTER | 두께=두꺼움, 기능=방풍 |
| `bottom` | 얇은 면 바지 | BOTTOM | 두께=얇음 |
| `top` | 면 반팔 티셔츠 | TOP | 두께=얇음, 소매=반팔 |

W03은 DTO를 직접 구성한 방어적 사례다. 현재 `Weather` 엔티티의 풍속은 필수이므로 운영 DB·API의 누락 오류를 재현한 결과로 해석하지 않는다. 민감도는 서버에서 기본값 3을 적용하는 `int`이며 날씨의 null 처리와 구분한다.

**W04 · 9℃·풍속 10m/s:** 아래 두 의상만 제공한다. 없는 아우터나 방풍 기능을 만들어내지 않아야 한다. 순서 1은 아래 표, 순서 2는 역순이다.

| 키 | 의상 제목 | 종류 | 등록 속성 |
| --- | --- | --- | --- |
| `top` | 보통 두께 긴팔 셔츠 | TOP | 두께=보통, 소매=긴팔 |
| `bottom` | 긴 면 바지 | BOTTOM | 두께=보통 |

W04에서 유효한 조합을 반환했다는 것이 강풍·추위에서 보온이 충분하다는 뜻은 아니다. 추천 이유의 보온성·체감 표현 전반은 별도 검토가 필요하다.

### HTTP 400 원인 확인

2026년 11월 25일, 로그인된 [Groq 오류 로그](https://console.groq.com/dashboard/logs?cursor=&only_errors=true)에서 **11월 23일에 발생한 원래 두 오류**의 상세 메시지를 확인했다.

| 사례 | 발생 시각(KST) | 공급자 오류 코드 | 검증 실패 위치 | 출력 토큰 |
| --- | --- | --- | --- | --- |
| C08 · 순서 1 | 11월 23일 17:17:08 | `json_validate_failed` | `/clothesIds/2`의 enum 검사 | 699 |
| C09 · 순서 2 | 11월 23일 17:23:38 | `json_validate_failed` | `/clothesIds/2`의 enum 검사 | 769 |

두 메시지 모두 `/properties/clothesIds/items/enum`에 대해 `value must be one of`라는 오류를 기록했다. 허용 목록은 각 평가 옷장의 ID 집합과 일치했다. 즉 **모델 응답의 세 번째 의상 ID가 요청 스키마에서 허용한 ID 목록에 없어 Groq가 응답을 거부한 것**이다. 오류 종류는 `invalid_request_error`이며, 우리 서버의 응답 검증 전에 HTTP 400이 반환됐다.

당시 출력 토큰은 각각 699개·769개로 설정 한도 2,048개에 도달하지 않았다. 따라서 이 두 건의 확인된 원인은 출력 ID의 enum 위반이다. 로그 메시지에는 실제로 잘못 생성한 ID 값이 표시되지 않아 구체적인 문자열 오타인지 임의 값 생성인지까지는 구분하지 않는다.

**토큰 한도 대조 실험은 별개다.** 과거 사례·프롬프트를 복원해 토큰 한도만 바꾼 8회 요청에서는 다음 결과가 나왔다. 모델·입력·스키마·추론 강도를 고정했고, 30초 간격으로 재시도 없이 진행했다.

| 출력 토큰 한도 | 요청 수 | 실제 결과 |
| --- | --- | --- |
| 기존 2,048 | 4회 | 모두 HTTP 200·정상 종료. 생성 토큰 680~808개 |
| 의도적으로 낮춘 64 | 2회 | 모두 HTTP 400, `invalid_request_error / json_validate_failed` |
| 대조용 4,096 | 2회 | 모두 HTTP 200·정상 종료. 생성 토큰 640~821개 |

64토큰에서 생성 실패가 같은 오류 코드로 나타났다는 사실만으로 과거 두 건도 토큰 부족이라고 판단할 수는 없었다. 과거 실제 로그를 확인한 결과는 ID enum 위반이었다. 운영 토큰 한도는 변경하지 않았다. 이 진단은 위 추천 품질 24회 평가와 합산하지 않는다.

모델·스키마 요청 형식은 [Groq 공식 지원 조건](https://console.groq.com/docs/structured-outputs)에 맞는지 확인했다. 임시 실행 코드·진단 파일은 제거하고 원인과 측정 결과만 이 문서에 남겼다.
