# 의상 추천 성능 검증 정리

이 검증은 **같은 옷과 날씨를 주었을 때, 기존 추천과 LLM을 활용한 추천 중 어느 쪽이 정해 둔 조건을 더 잘 지키는지** 비교한 것이다.

예를 들어 더운 날에는 겨울옷을 피하고, 비 오는 날에는 등록된 방수 기능을 고려하는지 확인했다. 색 조합이나 개인 취향까지 평가한 것은 아니다.

## 1. 비교 방법

옷장과 날씨가 다른 상황을 12개 만들었다. 각 상황에서 옷의 입력 순서를 바꿔 두 번씩 확인했으므로 한 번의 평가에 총 24번을 비교했다. 최초 상태와 프롬프트 수정 후 상태에서 이 평가를 각각 실행했다. 입력 순서를 바꾼 이유는 같은 점수의 옷 중 먼저 나온 옷만 고르는 영향을 확인하기 위해서다.

```text
같은 옷장 + 같은 날씨 + 같은 사용자 조건
                  ↓
        기존 추천과 LLM 추천 실행
                  ↓
      미리 정한 통과 기준으로 비교
```

| 상황 | 미리 정한 통과 기준 |
| --- | --- |
| 34도인데 겨울옷과 여름옷이 함께 있음 | 제목을 읽고 여름 반팔과 가벼운 하의를 선택 |
| 비 오는 22도 | 방수 재킷과 방수 신발을 선택 |
| 바람이 강한 9도 | 바람이 통하는 가디건 대신 방풍 재킷을 선택 |
| 제목은 여름옷인데 등록 속성은 두꺼운 긴팔임 | 제목보다 사용자가 등록한 속성을 우선 |

통과 기준은 추천 결과를 보기 전에 정했다. 한 상황에 정한 조건을 모두 지키면 통과로 계산했다.

## 2. 수정 전후 비교 결과

2026년 11월 23일, 근거 인용 규칙과 등록 속성 우선 예시를 보강한 뒤 같은 12개 사례를 같은 두 입력 순서로 다시 평가했다. 모델·날씨·속성·통과 기준은 유지했다. 기존 알고리즘의 15/24 결과도 그대로 재현됐다.

| 확인한 항목 | 최초 평가 | 수정 후 재평가 |
| --- | --- | --- |
| 기존 알고리즘 통과 | 15/24 · 62.5% | 15/24 · 62.5% |
| LLM을 연동한 최종 추천 통과 | 22/24 · 91.7% | **23/24 · 95.8%** |
| LLM 응답이 검사에 통과해 사용됨 | 11/24 · 45.8% | **22/24 · 91.7%** |
| 확인된 근거 문구 오류 | 13건 | **0건** |
| Groq 요청 오류 | 0건 | 2건 · HTTP 400 |
| LLM 처리 시간 중앙값 | 약 1.87초 | 약 2.35초 |

**근거를 잘못 인용해 응답을 버리는 문제는 이번 재평가에서 나오지 않았다.** 실제 응답이 반환된 22건 모두 근거 검사를 통과했고, 분석 특징을 빈 목록으로 생략한 경우도 없었다. HTTP 400인 두 요청은 모델 응답을 받지 못했으므로 근거 검사의 대상이 아니었다.

최종 추천에는 기존 알고리즘으로 돌아간 결과도 포함된다. 수정 후에는 LLM 응답 22건을 사용했고 요청 오류 2건에서 기존 추천을 사용했다. 그중 한 건은 통과했고 한 건은 실패했다.

### 좋아진 결과

겨울 상하의와 여름 원피스가 함께 있는 C10의 두 번째 회차가 새로 통과했다. 이전에는 원피스를 올바르게 골라도 근거 문구 오류로 겨울 상하의를 반환했는데, 수정 후에는 두 회차 모두 여름 원피스를 최종 추천했다.

제목과 등록 속성이 충돌하는 C11도 두 회차 모두 등록 속성에 맞는 옷을 골랐고 응답 검사까지 통과했다. 최초 평가에서 통과했던 회차가 이번에 새로 실패한 경우는 없었다.

### 남은 요청 오류

| 상황 | 발생한 일 | 최종 결과 |
| --- | --- | --- |
| C08 첫 번째 회차 · 강풍 9도 | Groq HTTP 400으로 기존 추천 사용 | 가디건이 선택되어 방풍 조건 실패 |
| C09 두 번째 회차 · 한여름 추가 아이템 | Groq HTTP 400으로 기존 추천 사용 | 여름 신발·양말이 선택되어 통과 |

실패한 요청을 재시도한 성공 결과로 바꾸지 않고 계획한 24회 그대로 집계했다. HTTP 400의 세부 원인은 이 평가에서 확정하지 않았다. 다음에는 이 요청 오류의 원인을 확인할 필요가 있다.

처리 시간은 중앙값 기준 약 0.48초 늘었다. 이 시간은 직렬화·Groq 통신·응답 해석·검사를 합친 값이며 DB·Redis·HTTP 컨트롤러·요청 사이 대기 시간은 제외했다. 통신 상황과 생성 결과도 달라질 수 있어 프롬프트 길이만의 영향으로 단정하지 않는다.

## 3. 발견한 문제와 수정 내용

### 근거 문구를 잘못 작성함

서버는 LLM이 설명한 특징의 근거가 실제 제목이나 속성 값에 있는지 검사한다.

```text
등록된 속성: 두께 = 얇음
올바른 근거: 얇음
잘못된 근거: 두께: 얇음
```

실제 속성 값에는 `얇음`만 있는데 이름까지 붙여서 인용하면 검사에 실패한다. 최초 평가에서는 근거 문구 오류가 13번 발생했다. 이를 줄이기 위해 원문 복사 규칙과 정상·오류 예시를 프롬프트와 응답 스키마에 보강했다.

최초 평가에서는 옷을 적절하게 골랐는데도 응답을 사용하지 못한 경우가 있었다. 방풍 재킷을 골랐지만 가디건으로 돌아가거나, 여름 원피스를 골랐지만 겨울 상하의로 돌아간 사례다.

### 제목과 등록 속성이 충돌할 때 잘못 판단함

```text
제목: 얇은 여름 반팔 티셔츠
등록 속성: 두꺼움 / 긴팔 / 울
날씨: 31도
```

이 상황에서 LLM이 위 옷을 선택한 사례가 한 번 있었다. 사용자가 등록한 속성을 우선해야 한다는 조건을 지키지 못한 것이다.

해당 응답은 별도의 근거 문구 오류로 거부되어 최종 추천에는 반영되지 않았다. 이후 같은 특징은 등록 속성을 우선한다는 규칙, 더운 날·추운 날의 충돌 예시, 선택과 설명의 일치 확인 지시를 보강했다. 수정 후 C11의 두 입력 순서에서는 이 문제가 재현되지 않았다.

## 4. 다음에 다시 검증하는 순서

1. **같은 상황을 준비한다.** 아래에 남긴 12개 사례의 옷·속성·날씨를 그대로 사용한다.
2. **통과 기준을 먼저 확인한다.** 예를 들어 비 오는 사례는 방수 재킷과 신발을 골라야 통과다.
3. **두 방법으로 추천한다.** 기존 알고리즘과 LLM에 같은 옷 순서·날씨·온도 민감도·직전 추천 조건을 사용한다.
4. **실제로 사용된 결과를 확인한다.** LLM이 고른 옷, 서버 검사 통과 여부, 최종 반환한 옷을 구분한다.
5. **표로 기록하고 비교한다.** 최종 통과 횟수, LLM 응답 사용 횟수, 새로 잘못 추천한 사례를 확인한다.

기록은 다음처럼 하면 된다.

| 상황 | 통과 기준 | 기존 추천 | LLM 원래 선택 | 최종 반환 | LLM 사용 여부 | 통과 여부 |
| --- | --- | --- | --- | --- | --- | --- |
| 비 오는 22도 | 방수 재킷·신발 선택 | 기록 | 기록 | 기록 | 사용 / 기존 추천으로 복구 | 통과 / 실패 |

API가 정상 응답했다고 해서 LLM 추천이 사용됐다고 볼 수는 없다. 실패해도 기존 추천을 반환하기 때문에, 개발 환경의 디버거나 임시 로그로 사용 여부와 복구 원인도 확인한다.

기존 API로 비교할 때는 `.env`의 `RECOMMENDATION_LLM_ENABLED`를 `false`, `true`로 바꾸고 각각 서버를 재시작한다. 직전 추천 기록이 결과에 영향을 주므로 테스트 사용자·날씨의 기록 상태도 같게 맞춘다. 이 방식의 API 전체 시간은 위의 LLM 처리 시간과 구분한다.

이후 프롬프트나 모델을 수정할 때도 **근거 문구를 정확히 인용하는지**, **제목보다 등록 속성을 우선하는지**를 같은 사례로 다시 확인한다. 요청 오류 때문에 기존 추천을 사용한 경우도 따로 기록한다. 결과가 좋아지도록 중간에 통과 기준을 바꾸지 않는다.

## 5. 결과를 해석할 때 주의할 점

표의 통과율은 아래에 만든 상황에서 조건을 지킨 비율이다. 실제 모든 사용자의 만족도나 전체 추천 정확도를 뜻하지 않는다. 사례의 절반은 기존 알고리즘이 잘 처리하지 못하는 제목·자유 속성을 일부러 다뤘다.

같은 상황을 순서만 바꿔 두 번 확인했으므로, 서로 다른 실제 사용자 사례 24개를 평가한 것으로 볼 수도 없다. 특히 C11은 실패했던 예시를 수정된 프롬프트에 직접 넣었으므로 이미 알려준 문제를 다시 확인한 결과다. 처음 보는 충돌 사례에도 잘 대응하는지는 추가 확인이 필요하다. 같은 프롬프트와 모델을 사용해도 새 응답은 달라질 수 있다. 개인 취향이나 코디의 미적 조화는 실제 사용자의 비교 평가가 더 필요하다.

### 당시 구현에서 확인한 위치

## 상세 사례

속성이 적혀 있지 않은 특징을 두께·소매 속성으로 미리 보충하지 않는다. 예를 들어 C05·C06은 제목에만 두께·계절 표현이 있으므로 등록 속성을 그대로 사용해야 한다.

### C01 명시 속성: 한여름 32도

기온 32도, 민감도 3, 풍속 2m/s. 나머지 날씨 값은 아래 고정 조건 표를 따른다.

| 키 | 의상 제목 | 종류 | 등록 속성 |
| --- | --- | --- | --- |
| `warm_top` | 울 긴팔 니트 | TOP | 두께=두꺼움, 소매=긴팔 |
| `cool_top` | 면 반팔 티셔츠 | TOP | 두께=얇음, 소매=반팔 |
| `warm_bottom` | 겨울 기모 바지 | BOTTOM | 두께=두꺼움 |
| `cool_bottom` | 여름 반바지 | BOTTOM | 두께=얇음 |

통과 기준:

- 얇은 반팔 상의 선택
- 얇은 하의 선택

첫 입력 순서: `cool_bottom` → `warm_top` → `cool_top` → `warm_bottom`

두 번째 입력은 이 순서의 역순이다.

### C02 명시 속성: 겨울 3도

기온 3도, 민감도 3, 풍속 2m/s. 나머지 날씨 값은 아래 고정 조건 표를 따른다.

| 키 | 의상 제목 | 종류 | 등록 속성 |
| --- | --- | --- | --- |
| `warm_top` | 두꺼운 긴팔 니트 | TOP | 두께=두꺼움, 소매=긴팔 |
| `cool_top` | 얇은 반팔 티셔츠 | TOP | 두께=얇음, 소매=반팔 |
| `warm_bottom` | 두꺼운 겨울 바지 | BOTTOM | 두께=두꺼움 |
| `cool_bottom` | 얇은 여름 바지 | BOTTOM | 두께=얇음 |
| `warm_outer` | 두꺼운 겨울 패딩 | OUTER | 두께=두꺼움 |
| `cool_outer` | 얇은 여름 재킷 | OUTER | 두께=얇음 |

통과 기준:

- 두꺼운 긴팔 상의 선택
- 두꺼운 하의 선택
- 두꺼운 아우터 선택

첫 입력 순서: `cool_bottom` → `warm_bottom` → `warm_outer` → `cool_outer` → `cool_top` → `warm_top`

두 번째 입력은 이 순서의 역순이다.

### C03 명시 속성: 온화한 21도

기온 21도, 민감도 3, 풍속 2m/s. 나머지 날씨 값은 아래 고정 조건 표를 따른다.

| 키 | 의상 제목 | 종류 | 등록 속성 |
| --- | --- | --- | --- |
| `medium_top` | 보통 두께 반팔 셔츠 | TOP | 두께=보통, 소매=반팔 |
| `light_top` | 얇은 반팔 티셔츠 | TOP | 두께=얇음, 소매=반팔 |
| `heavy_top` | 두꺼운 겨울 니트 | TOP | 두께=두꺼움, 소매=긴팔 |
| `medium_bottom` | 보통 두께 슬랙스 | BOTTOM | 두께=보통 |
| `light_bottom` | 얇은 면 바지 | BOTTOM | 두께=얇음 |
| `winter_outer` | 겨울 패딩 | OUTER | 두께=두꺼움 |

통과 기준:

- 보통 또는 얇은 상의 선택
- 보통 또는 얇은 하의 선택
- 겨울 패딩 제외

첫 입력 순서: `light_top` → `winter_outer` → `heavy_top` → `light_bottom` → `medium_top` → `medium_bottom`

두 번째 입력은 이 순서의 역순이다.

### C04 명시 속성: 추위를 타는 사용자 17도

기온 17도, 민감도 1, 풍속 2m/s. 나머지 날씨 값은 아래 고정 조건 표를 따른다.
