# 의상 추천 성능 검증 정리

이 검증은 **같은 옷과 날씨를 주었을 때, 기존 추천과 LLM을 활용한 추천 중 어느 쪽이 정해 둔 조건을 더 잘 지키는지** 비교한 것이다.

예를 들어 더운 날에는 겨울옷을 피하고, 비 오는 날에는 등록된 방수 기능을 고려하는지 확인했다. 색 조합이나 개인 취향까지 평가한 것은 아니다.

## 1. 비교 방법

옷장과 날씨가 다른 상황을 12개 만들었다. 각 상황에서 옷의 입력 순서를 바꿔 두 번씩 확인했으므로 총 24번 비교했다. 입력 순서를 바꾼 이유는 같은 점수의 옷 중 먼저 나온 옷만 고르는 영향을 확인하기 위해서다.

```text
같은 옷장 + 같은 날씨 + 같은 사용자 조건
                  ↓
        기존 추천과 LLM 추천 실행
                  ↓
      미리 정한 통과 기준으로 비교
```

| 상황 | 미리 정한 통과 기준 |
| --- | --- |
| 34도인데 겨울옷과 여름옷이 함께 있음 | 제목을 읽고 여름 반팔과 가벼운 하의를 선택 |
| 비 오는 22도 | 방수 재킷과 방수 신발을 선택 |
| 바람이 강한 9도 | 바람이 통하는 가디건 대신 방풍 재킷을 선택 |
| 제목은 여름옷인데 등록 속성은 두꺼운 긴팔임 | 제목보다 사용자가 등록한 속성을 우선 |

통과 기준은 추천 결과를 보기 전에 정했다. 한 상황에 정한 조건을 모두 지키면 통과로 계산했다.

## 2. 비교 결과

2026년 11월 23일, 당시 코드와 프롬프트를 그대로 사용해 실제 Groq를 호출했다.

| 비교 대상 | 기준을 모두 지킨 횟수 |
| --- | --- |
| 기존 알고리즘 | 24번 중 15번 · 62.5% |
| LLM을 연동한 최종 추천 | 24번 중 22번 · 91.7% |

**이번에 준비한 상황에서는 최종 추천이 7번 더 적절해졌다.** 특히 제목의 여름·겨울 표현이나 방수·방풍 같은 속성을 활용하는 상황에서 개선됐다.

다만 최종 추천에는 LLM에 문제가 생겨 기존 알고리즘으로 돌아간 결과도 포함된다.

| 실제 처리 | 횟수 |
| --- | --- |
| LLM 응답이 서버 검사를 통과해 사용됨 | 11번 |
| LLM 응답을 사용하지 못해 기존 추천을 사용함 | 13번 |

**추천을 더 잘 고르는 장점은 확인했지만, LLM 응답을 안정적으로 사용하는 부분은 개선이 필요하다.**

LLM 처리 시간은 중앙값 약 1.87초였다. 이는 Groq 통신·응답 해석·검사 등을 합친 시간이며 DB 조회나 API 전체 처리 시간은 제외한 값이다.

## 3. 발견한 문제

### 근거 문구를 잘못 작성함

서버는 LLM이 설명한 특징의 근거가 실제 제목이나 속성 값에 있는지 검사한다.

```text
등록된 속성: 두께 = 얇음
올바른 근거: 얇음
잘못된 근거: 두께: 얇음
```

실제 속성 값에는 `얇음`만 있는데 이름까지 붙여서 인용하면 검사에 실패한다. 이번에는 근거 문구 오류가 13번 발생했다.

그중에는 옷을 적절하게 골랐는데도 응답을 사용하지 못한 경우가 있었다. 방풍 재킷을 골랐지만 가디건으로 돌아가거나, 여름 원피스를 골랐지만 겨울 상하의로 돌아간 사례다.

### 제목과 등록 속성이 충돌할 때 잘못 판단함

```text
제목: 얇은 여름 반팔 티셔츠
등록 속성: 두꺼움 / 긴팔 / 울
날씨: 31도
```

이 상황에서 LLM이 위 옷을 선택한 사례가 한 번 있었다. 사용자가 등록한 속성을 우선해야 한다는 조건을 지키지 못한 것이다.

해당 응답은 별도의 근거 문구 오류로 거부되어 최종 추천에는 반영되지 않았다. 따라서 근거 형식과 함께 이 판단 문제도 수정해야 한다.

## 4. 다음에 다시 검증하는 순서

1. **같은 상황을 준비한다.** 아래에 남긴 12개 사례의 옷·속성·날씨를 그대로 사용한다.
2. **통과 기준을 먼저 확인한다.** 예를 들어 비 오는 사례는 방수 재킷과 신발을 골라야 통과다.
3. **두 방법으로 추천한다.** 기존 알고리즘과 LLM에 같은 옷 순서·날씨·온도 민감도·직전 추천 조건을 사용한다.
4. **실제로 사용된 결과를 확인한다.** LLM이 고른 옷, 서버 검사 통과 여부, 최종 반환한 옷을 구분한다.
5. **표로 기록하고 비교한다.** 최종 통과 횟수, LLM 응답 사용 횟수, 새로 잘못 추천한 사례를 확인한다.

기록은 다음처럼 하면 된다.

| 상황 | 통과 기준 | 기존 추천 | LLM 원래 선택 | 최종 반환 | LLM 사용 여부 | 통과 여부 |
| --- | --- | --- | --- | --- | --- | --- |
| 비 오는 22도 | 방수 재킷·신발 선택 | 기록 | 기록 | 기록 | 사용 / 기존 추천으로 복구 | 통과 / 실패 |

API가 정상 응답했다고 해서 LLM 추천이 사용됐다고 볼 수는 없다. 실패해도 기존 추천을 반환하기 때문에, 개발 환경의 디버거나 임시 로그로 사용 여부와 복구 원인도 확인한다.

기존 API로 비교할 때는 `.env`의 `RECOMMENDATION_LLM_ENABLED`를 `false`, `true`로 바꾸고 각각 서버를 재시작한다. 직전 추천 기록이 결과에 영향을 주므로 테스트 사용자·날씨의 기록 상태도 같게 맞춘다. 이 방식의 API 전체 시간은 위의 LLM 처리 시간과 구분한다.

다음 수정에서는 **근거 문구를 정확히 인용하는지**, **제목보다 등록 속성을 우선하는지**를 먼저 개선하고 같은 사례로 다시 확인한다. 결과가 좋아지도록 중간에 통과 기준을 바꾸지 않는다.

## 5. 결과를 해석할 때 주의할 점

91.7%는 아래에 만든 상황에서 조건을 지킨 비율이다. 실제 모든 사용자의 만족도가 91.7%라는 뜻은 아니다. 사례의 절반은 기존 알고리즘이 잘 처리하지 못하는 제목·자유 속성을 일부러 다뤘다.

같은 상황을 순서만 바꿔 두 번 확인했으므로, 서로 다른 실제 사용자 사례 24개를 평가한 것으로 볼 수도 없다. 같은 프롬프트와 모델을 사용해도 새 응답은 달라질 수 있다. 개인 취향이나 코디의 미적 조화는 실제 사용자의 비교 평가가 더 필요하다.

## 상세 사례

속성이 적혀 있지 않은 특징을 두께·소매 속성으로 미리 보충하지 않는다. 예를 들어 C05·C06은 제목에만 두께·계절 표현이 있으므로 등록 속성을 그대로 사용해야 한다.

### C01 명시 속성: 한여름 32도

기온 32도, 민감도 3, 풍속 2m/s. 나머지 날씨 값은 아래 고정 조건 표를 따른다.

| 키 | 의상 제목 | 종류 | 등록 속성 |
| --- | --- | --- | --- |
| `warm_top` | 울 긴팔 니트 | TOP | 두께=두꺼움, 소매=긴팔 |
| `cool_top` | 면 반팔 티셔츠 | TOP | 두께=얇음, 소매=반팔 |
| `warm_bottom` | 겨울 기모 바지 | BOTTOM | 두께=두꺼움 |
| `cool_bottom` | 여름 반바지 | BOTTOM | 두께=얇음 |

통과 기준:

- 얇은 반팔 상의 선택
- 얇은 하의 선택

첫 입력 순서: `cool_bottom` → `warm_top` → `cool_top` → `warm_bottom`

두 번째 입력은 이 순서의 역순이다.
